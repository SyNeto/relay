# relay

You are supervising a `relay`-driven lifecycle: from an early, still-open decision through drafting a spec
to executing it against a target repo. The full protocol is in `CONTRACT.md` in the `relay` install — this
skill is the condensed, Claude Code-specific version of it. If anything here and `CONTRACT.md` disagree,
`CONTRACT.md` is authoritative.

**Precondition.** Run `relay --version`. If the command isn't found, stop and tell the user how to install
it (`pipx install git+https://github.com/SyNeto/relay.git`) — don't try to work around a missing install.

## Four capabilities, one shared discipline

| Command | Stateful? | What it's for |
|---|---|---|
| `relay review run` | No | independent, advisory critique of a still-open decision — never a gate |
| `relay spec draft` | No | draft a whole spec document from a change request + gathered context |
| `relay run` / `relay finding` / `relay fix run` | Yes | iterate a target repo through find -> fix -> validate against a severity gate |
| `relay repo setup` / `relay repo commit` / `relay repo push` / `relay repo pr create` | Reads run state, writes local git and remote | isolate a run's branch, stage+commit its fixed-finding files, push, and open a PR |

Across all four, the same split holds: **judgment stays with you** — deciding what's actually wrong, what
a spec should say, whether a decision is sound, whether a fix is correct, when this iteration's work is
actually done. `relay` mechanizes the model call and, for the fix loop, applies the result, tracks state,
and (optionally) the local git plumbing around it. Never treat a model's output — a review, a draft, or a
fix — as correct just because it came back cleanly formatted.

## When the user brings you a fuzzy idea

Not every request needs every stage below — a small, obviously-right fix goes straight into the find ->
fix -> validate loop. Reach for the earlier stages when it's a feature, a significant change, or something
you or the user are genuinely unsure about:

1. **Clarify with the user.** What's the actual problem or goal? Gather the context that bears on it —
   existing docs, relevant code, prior discussion — as files you can pass with `--context-file`.

2. **Decision review**, if the choice itself is worth a second opinion (should this be built at all, is
   this the right approach, is a risk being underweighted):
   ```
   relay review run --decision "..." --context-file ... [--context-file ...] \
     --provider <a DIFFERENT provider than whatever reasoned about this> \
     --output REVIEW.md
   ```
   Prefer a different `--provider` than whatever produced the reasoning under review — that's what makes it
   a genuine second opinion instead of the same reasoning checking itself. The result is **advisory input
   only**: read it, weigh it against your own judgment and the user's, and report it to them before
   proceeding. It never blocks or approves anything on its own, and there's no decline form for it — even a
   thinly-supported decision gets reviewed, with the thinness named as part of the critique.

3. **Draft the spec**, once you and the user are actually proceeding:
   ```
   relay spec draft --request "..." --context-file ... [--context-file ...] --output SPEC.md
   ```
   Review the draft yourself before it's saved anywhere permanent — same rule as the fix loop's Validate: a
   model's draft is a starting point you're accountable for, not a finished artifact.
   When the run is headed toward a real publish, move the drafted spec into the target repo (e.g. `docs/specs/`)
   before referencing it with `run start --spec-file` — otherwise `repo commit`/`repo pr create` will warn that
   the `Spec-File:` trailer points nowhere anyone else can resolve.

4. **Execute it** — decompose the (now-reviewed) spec into findings and run the loop below. Which parts of
   the spec become which findings is still your judgment call; `relay` has no opinion about what a spec
   means. Start the run with `--spec-file SPEC.md` so it stays traceable back to why it exists, and pair it
   with `relay repo setup` right after Start to isolate the work on its own branch before Find/Fix touch
   anything — see "Per iteration"'s Start and Commit steps below. Once the branch is ready and the run is
   stopping with a clean gate, `relay repo push` and `relay repo pr create` can publish it.

5. **Optional closing check**, for larger or riskier work: once the loop below reaches a clean gate, run
   `relay review run` once more, this time asking whether the implementation still matches the original
   intent:
   ```
   relay review run --decision "does this diff actually deliver on the spec?" \
     --context-file SPEC.md --diff-from-branch <base_branch> --target-repo-root <target_repo_root>
   ```
   `--diff-from-branch` gathers `git diff <base_branch>...HEAD` automatically — no need to hand-assemble a
   summary of what changed. Same advisory framing; use it where spec/implementation drift would be costly
   to miss, skip it for small mechanical work.

## The two roles you own in the fix loop

`relay` mechanizes state, the model call, applying the fix, and gate evaluation. It does **not** — and
should not — automate two things, because they require judgment:

- **Find**: deciding what's actually wrong with the target and recording it as a finding.
- **Validate**: reading the diff `relay fix run` produces and deciding whether to accept it.

**Never skip Validate, and never treat a model-produced diff as correct just because it applied cleanly.**
In a real run, roughly 1 in 10 accepted fixes needed a hand correction after review (a type mismatch, a
broken test, a dangling markdown fence) — reviewing every diff before marking it `fixed` is the entire
reason this loop is safer than a single unreviewed model pass.

## Per iteration

Run id convention: `YYYY-MM-DD-runN`. Ask the user for `<target_repo_root>` and severities to gate on if
not already clear from context (e.g. `CRITICAL,HIGH` first, `MEDIUM,LOW` in a later run).

1. **Start.**
   ```
   relay run start <run_id> --max-iterations 3 --gate-severities CRITICAL,HIGH [--spec-file SPEC.md]
   ```
   `--spec-file` is optional — add it when this run traces back to a drafted spec, per the lifecycle above.
   Right after Start, while the tree is still clean, `relay repo setup <run_id> <target_repo_root>` isolates
   this run's work on its own branch (default `relay/<run_id>`) before Find/Fix touch anything — also
   optional, see step 5 (Commit) for the matching `relay repo commit`.

2. **Find** (you). Review the target — first iteration is a fresh pass, or a decomposition of the spec from
   the lifecycle above; later iterations focus on files touched by the previous iteration's fixes (did the
   fix hold up / ripple anywhere) plus any finding left `open` from before. For each issue, record it —
   `id`, `severity`, `summary`, `file`, `target_excerpt` (copy verbatim from the file, don't retype by hand
   if you can slice it programmatically), `failure_scenario`, optional `section`/`reference`:
   ```
   echo '{"id": "...", "severity": "HIGH", "summary": "...", "file": "...",
          "target_excerpt": "...", "failure_scenario": "..."}' | relay finding record <run_id>
   ```
   (Also accepts a JSON array for multiple findings at once, or `--from-json <path>`.)

3. **Fix**, one finding at a time:
   ```
   relay fix run <run_id> <finding_id> <target_repo_root>
   ```
   This calls the model, applies the extracted fix directly to the file, and prints a diff. Nothing is
   marked or committed yet. Large excerpts can need more than the 90s default —
   `--timeout 240` if a call times out on something sizeable.

4. **Validate** (you). Read the diff. Does it actually resolve the finding? Did it stay in scope? Does it
   match the reference (if any) without being pasted verbatim? Then:
   - accept: `relay finding mark <run_id> <finding_id> fixed`
   - reject: revert the file (`git checkout -- <file>` in the target repo), then
     `relay finding mark <run_id> <finding_id> open` — either refine the finding and re-run step 3, or fix
     it by hand and mark `fixed` once it's actually right. Don't spend unlimited retries against the same
     prompt.
   - if the model declines with `CANNOT_FIX`, that can be **correct behavior**, not a bug to route around
     — e.g. it should refuse a fix that's actually a deletion if its instructions only allow rewriting. Do
     the fix by hand in that case rather than loosening the model's instructions mid-run.

5. **Commit.** Once this iteration's fixes are validated:
   ```
   relay repo commit <run_id> <target_repo_root>
   ```
   Stages and commits exactly this run's `fixed`-finding files that are still dirty (refuses loudly if none
   are). Pair with `relay repo setup <run_id> <target_repo_root>` right after Start, before Find/Fix touch
   anything, to isolate the run's work on a dedicated branch (default `relay/<run_id>`). Both are optional
   convenience wrappers — you can still do this entirely by hand with plain `git` instead.

6. **Check.**
   ```
   relay run status <run_id>
   ```
   If not stopping and `iteration < max_iterations`: go to step 1 for the next iteration. If stopping:
   report the final render to the user — either a clean pass on the gated severities, or the
   max-iteration cutoff with whatever's still open.

## Notes

- `relay fix run` fails loudly if `target_excerpt` isn't found verbatim in its file (shifted or
  already-changed) or matches more than once (ambiguous) — that's a signal to re-derive the excerpt during
  Find, not to force it through. `relay finding verify <run_id> <target_repo_root>` checks every open
  finding's excerpt before you spend a model call on it — worth running right after a Find pass.
- Every model-facing command has its own strict response envelope (fix: `FIXED_EXCERPT`/`CANNOT_FIX`; spec
  draft: `SPEC_DRAFT`/`INSUFFICIENT_CONTEXT`; review run: `REVIEW`, no decline form) — a response that
  doesn't match hard-fails rather than being guessed at. That's `relay` refusing to paper over a bad model
  response; don't work around it by loosening prompts or hand-parsing the raw output yourself.
- Request volume is shared across every run on this machine, per provider (one account/API-key quota each)
  — `relay quota status` shows rpm/1h/24h counts if a call fails unexpectedly.
- Asked to resume a run but don't have its `run_id`? `relay run list` prints one summary line per run found
  under `--state-dir` (iteration, phase, gate status, spec) — no need to have it memorized.
- After a release, `relay repo sync-dev` (0.9.0+) rebases `dev` onto `main` and force-pushes with lease,
  but only when invoked with `--i-understand-this-rewrites-dev-history` so the history rewrite is explicit
  — CONTRACT.md's Repository management > Post-release dev sync section documents the six-step safety sequence.
